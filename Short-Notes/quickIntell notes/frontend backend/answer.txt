### RBAC Frontend↔Backend Contract — Step-by-Step Q&A

Below are the exact questions HR and other teams ask most, with clear, step‑by‑step answers based on the current code.

### 1) How does the backend decide if a user can read/write data?
- The server looks up the user’s `OrganizationMember` row for the active organization, then builds a CASL ability from role + fine-grained permissions.
- Owner role gets full manage rights within the org; others are controlled by four fields:
  - recordPermission: read/write EOB records
  - uploadRecordPermission: create/upload EOB records
  - manageUserPermission: read/write org members
  - organizationDetailsPermission: read/write org profile/settings

  can('delete', 'OrganizationMember', { organizationId })

### 10) How can the frontend know what UI to show/disable?
- Fetch members for the current org and find the current user’s `OrganizationMember` row. Use `role` and fine‑grained fields to gate UI (e.g., show Invite button only if owner or `manageUserPermission = WRITE`).

### 11) How does this pattern extend to medical coding or payments?
- Add fine‑grained fields for the new domain (e.g., `codingPermission`, `claimsPermission`) on `OrganizationMember`.
- Map them to CASL actions in the ability builder.
- Require those actions in the relevant operations and filter with `accessibleBy(ability)`.
- Frontend continues to send: target resource identifiers, minimal update/create payloads, and (for invites) the exact domain permissions to assign.

Notes
- Current behavior for EOB list: server infers the organization from the user’s first membership. If multiple orgs are needed, we can add an explicit `organizationId` argument in requests.
